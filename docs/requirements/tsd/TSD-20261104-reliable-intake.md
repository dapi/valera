# Technical Specification: надёжность обращений

**Статус:** Production
**Сложность:** Medium
**Приоритет:** High
**Создан:** 04.11.2026
**User Story:** [Надёжность обращений](../user-stories/US-20261104-reliable-intake.md)

## Архитектура
- PostgreSQL inbox `telegram_updates`: tenant, уникальный update_id внутри tenant, payload, ключ чата, processed_at/failed_at. Webhook проверяет secret, атомарно сохраняет запись и GoodJob, быстро возвращает 200. Ошибка БД/очереди отдаёт 500 для повтора Telegram.
- Job использует транзакционную advisory lock по tenant/чату и блокировку inbox-записи. Обработанные записи пропускаются; ожидающие более раннего сообщения повторяются. После исчерпания попыток failed_at позволяет продолжить чат; ошибка остаётся в GoodJob/ErrorLogger.
- Долгая транзакция ограничена одним диалогом и удерживает соединение на время LLM. Для пилота это осознанная цена согласованности. Перед ростом нагрузки измерить занятость пула.
- `Current.telegram_update` передаёт ключ операции инструменту; уникальный nullable FK заявки защищает повтор инструмента. Заявка, аналитика, уведомление и классификация ставятся в GoodJob в общей PostgreSQL-транзакции, без after_commit enqueue.
- Номер выдаётся под блокировкой tenant до MAX+1. Транзакция сохраняет уникальность при параллельных сохранениях.
- HTTP 429/5xx выделяются в transient-ошибку с retry_after, остальные Telegram API ошибки постоянные. Статус уведомления хранится на заявке. Успешный внешний send и commit не образуют распределённую транзакцию: авария между ними может повторить ответ/уведомление, но не создать второй сохранённый лид.
- Обработанный payload очищается по retention, идентификаторы дедупликации остаются. Очередь и inbox используют primary DB; enqueue не откладывается до commit.
- Два общих login-лимита через Rails cache: IP и SHA256 нормализованного email, общий scope между главным доменом и tenant. Порог и окно — ApplicationConfig.

## План и проверка
1. Rails 8.1.4.1, атомарная постановка задач, inbox, инструмент и доставка.
2. Регрессии повторов, отката при enqueue/analytics failure, конкурентного сохранения, порядка и retry_after.
3. Login-лимиты и мобильная навигация; браузерная проверка.
4. Аудит, полный suite, сборка и штатный Helmfile-выпуск. Миграции аддитивные; откат образа сохраняет новые таблицы.

Статусы Draft → BusinessAnalyzes → SystemAnalyzes → Ready → In Progress пройдены 04.11.2026 на основании согласованного ревью и выбранного дизайна. Открытые эксплуатационные вопросы: end-to-end почта, восстановление backup, p95/нагрузка.
