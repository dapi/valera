## Эксплуатационные ограничения

Job держит транзакцию и соединение БД на время диалога; advisory lock сериализует один чат. Счётчики/нумерация могут кратковременно сериализовать сохранения в одном tenant. Production worker ограничен двумя execution threads при существующем пуле из пяти соединений: два соединения нужны GoodJob для служебной работы, одно оставлено в запасе. CPU/RAM limits не менялись.

Сохранение данных и очереди атомарно в primary PostgreSQL. Внешний sendMessage не входит в эту транзакцию: авария после отправки, но до commit, может привести к повторному ответу/уведомлению. Гарантия exactly-once внешней доставки не даётся. Для масштабирования нужны замеры p95, занятости пула и очереди.

При откате на 0.43.0 учитывать, что старый worker не знает класс TelegramUpdateJob: принятые inbox-записи нужно сохранить и обработать исправленным worker, а не удалять вместе с очередью.

Inbox с `failed_at` доступен эксплуатации через Rails runner/GoodJob dashboard; перед повтором проверить причину и сохранность payload. Обработанные payload очищаются через 7 дней; идентификаторы дедупликации сохраняются. Старые заявки без данных о доставке отображаются как «статус не сохранён».
